## Purpose

A **pre-flight invocation** is a mandatory readiness gate that runs
**before** a session execution prompt is generated for a Work Packet
(WP). It exists to:

- Confirm the WP is **sequenced correctly** — every prerequisite WP is
  `✅ Done` per `03-ROADMAP.md`
- Confirm the repo is **green** — `npm ci && npm run build` succeeds,
  reproducibility holds, Lighthouse ≥ 90 on touched pages
- Lock **scope** — explicit allowed and forbidden file globs, with the
  rule "anything not explicitly allowed is forbidden"
- Surface and resolve **risks** before code is written
- Verify the **cross-site contract** is preserved across the change
- Produce a binary **READY TO EXECUTE / NOT READY** verdict

Pre-flight is an audit artifact. It must read so a future contributor
can understand why execution was authorized without re-reading
transcripts.

This site is the public face of Legendary Arena. `static/brand-tokens.css`
is a cross-origin API contract consumed by `play.legendary-arena.com`
and `cards.legendary-arena.com` per `01-VISION.md` Cross-site contract.
Silent drift breaks downstream consumers. Pre-flight is the gate that
keeps drift out of the live URL.

---

## When Pre-Flight Is Required

Pre-flight is **mandatory** when the WP's allowlist (or its likely
allowlist before scope lock) touches any of:

- `static/brand-tokens.css` — cross-site API contract surface
- `static/_headers` — CORS and Cache-Control posture (per WP-006 lock)
- `static/_redirects` — known no-op under CF Pages but reserved
- `hugo.toml` — site config
- `themes/PaperMod` submodule pointer
- Cloudflare zone settings on the `legendary-arena.com` zone
  (per WP-006 lock: AI Crawl Control OFF, Managed `robots.txt` OFF,
  Browser Cache TTL "Respect Existing Headers", any Page Rule or
  Redirect Rule)
- Pagefind index, lazy-load contract, or keyboard policy
  (per WP-005 lock)
- `package.json` / `package-lock.json` — Pagefind or build dep changes
- Any `_index.md` or section-front-matter change that alters the
  navigation tree
- Any new top-level page or section

Pre-flight is **recommended but optional** for content-only WPs
(`content/posts/**`, `content/pages/**`) where only prose changes and
no new section is introduced.

Pre-flight is **not required** for `docs/**` edits that don't touch a
locked governance doc (`01-VISION.md`, `03-ROADMAP.md`,
`04-CONTENT-CONVENTIONS.md`, `01.2-bug-handling.md`,
`01.3-commit-hygiene.md`, this file, `docs/brand/**`).

Pre-flight is **not required** for `FIX:` or `POST:` commits. These
prefixes are the **content lane** defined in
`01.3-commit-hygiene.md` §Content-lane edits — they are hook-limited
to `content/**` + `static/images/**`, which by construction cannot
touch any of the gates above (no `static/brand-tokens.css`, no
`static/_headers`, no `static/_redirects`, no `hugo.toml`, no theme
pointer, no `_headers`/`_redirects`, no `package.json`). If a change
needs to escape the content lane, it stops being `FIX:`/`POST:` and
becomes a WP — at which point this gate applies again.

## Workflow Position

Pre-flight is **step 1** in the marketing-repo WP workflow. The
sequence is shorter than the engine repo's — there is no Execution
Checklist (EC) layer, no separate copilot-check step (folded into
§Known Failure Modes Lens below), and no Foundation Prompt gate.

| Step | Gate | When | Document |
|---|---|---|---|
| 0 | Session context (optional) | Start of session | `docs/ai/session-context/session-context-wpXXX.md` (only if a prior WP produced one) |
| 1 | Pre-flight | Before session prompt | this doc |
| 2 | Session prompt | Before execution | `docs/ai/invocations/session-wpXXX-*.md` |
| 3 | Execution | New Claude Code session | runs the session prompt |
| 4 | Pre-commit review (optional) | Before commit | reviewer eyes |
| 5 | Commit | Commit hygiene | `01.3-commit-hygiene.md` |
| 6 | Lessons learned | After commit | this doc, §Lessons Learned Template |

Sequencing rules:

- Step 1 produces a binary verdict. `NOT READY` blocks step 2.
- Step 2 (session prompt) may be authored in the same session as
  pre-flight, but step 3 (execution) runs in a **new** Claude Code
  session — the session that authored the prompt is not the session
  that runs it.
- Step 4 is optional but recommended for any WP touching the cross-site
  contract or Cloudflare zone state.
- Step 6 updates the Precedent Log below if the WP surfaced a
  preventable gap; otherwise it is a no-op.

### Dependency Check

Confirm every prerequisite WP listed in `03-ROADMAP.md` is `✅ Done`.
Read the roadmap directly — do not trust memory.

| Prereq WP | Status in `03-ROADMAP.md` | Lock date | Notes |
|---|---|---|---|
| WP-AAA | ✅ Done | YYYY-MM-DD | |
| WP-BBB | ✅ Done | YYYY-MM-DD | |

**Rule:** If any prerequisite is not `✅ Done`, pre-flight is
**NOT READY**. Do not start a WP whose dependencies are still in flight,
even if the executor "can see" how the dependency will land.

#### Authority commit verification

If the session prompt cites a **specific commit SHA** as the
authoritative version of any document (e.g., "WP-007b body at commit
`4433747`" or "the hardened WP body, commit `XXXXXXX`"), verify the
commit is reachable from `origin/main`:

```pwsh
git fetch origin main
git merge-base --is-ancestor <cited-sha> origin/main
# Exit 0 = reachable (cited authority is on main); pre-flight CAN proceed.
# Exit 1 = NOT reachable (cited authority lives on an unmerged branch);
#          pre-flight is NOT READY. STOP and surface to operator.
```

**Rule:** If the cited authority commit is not on `origin/main`,
pre-flight is **NOT READY**. The session is about to execute against
a version of the document that doesn't exist in the canonical
history. Resolution paths:

1. **Merge the cited commit's PR first.** Then re-run pre-flight after
   `git pull --ff-only origin main` brings the cited commit into the
   working branch's base.
2. **Abandon the cited commit's branch** (close its PR without
   merging) and **regenerate the session prompt** to remove the
   commit citation, defaulting to "WP body as it exists on
   `origin/main`."

Never proceed with execution against an unmerged authority — the
working tree will diverge from the cited truth, producing audit
chaos and re-execution.

**Empirical precedent (2026-05-11):** WP-007b's execution session
cited a hardening commit (`4433747`) that lived only on an open
SPEC PR. The session correctly stopped here at pre-flight. The
operator chose resolution path 2 (abandoned the SPEC PR, accepted
the loss of 9 audit-review improvements) to end the parallel
coordination cost between the hardening pass and the execution
session. The execution then proceeded against the WP body as it
existed on `origin/main`.

### Repo-Green Check

At the HEAD of the working branch (clean working tree, no staged
changes), verify:

- [ ] `npm ci && npm run build` succeeds with zero errors and zero
      warnings (the build script resolves to `hugo --minify && npx
      pagefind --site public` per `04-CONTENT-CONVENTIONS.md`
      §Build pipeline)
- [ ] Two consecutive `npm ci && npm run build` runs produce
      byte-identical `public/` (mechanical reproducibility per
      WP-005 § Step 8.7 — `Compare-Object` over SHA-256 hashes
      returns empty)
- [ ] Lighthouse ≥ 90 across all four categories (Performance,
      Accessibility, Best Practices, SEO) on the home page, the blog
      index, and any pillar page the WP will touch
- [ ] No console errors on production-mode pages
- [ ] `git submodule status` shows `themes/PaperMod` clean (no `+`
      flag — submodule pointer at the locked SHA)
- [ ] No staged files match the forbidden-staging list from
      `01.3-commit-hygiene.md` § Common Errors and Fixes
      (`.env`, `node_modules/`, `public/`, `resources/`,
      `.hugo_build.lock`, `lighthouse-*.json`, credentials)

If any check fails, pre-flight is **NOT READY** until the working tree
is restored to green.

### Cross-Site Contract Impact Review

This section is **mandatory** for any WP whose allowlist touches:

- `static/brand-tokens.css`
- `static/_headers`
- `static/_redirects`
- Any Cloudflare zone setting affecting how the above ship
- `docs/brand/palette.md`, `typography.md`, `spacing.md`, or
  `CHANGELOG.md` (since these are the contract's documentation)

For all other WPs, write:

> N/A — WP allowlist does not touch the cross-site contract surface.

Classify the change as exactly one of:

- **Additive (forward-compatible v1)** — new tokens added, existing
  tokens unchanged in name and semantic role. Consumers continue to
  resolve current names to current values. No coordinated update
  needed.
- **Breaking (v1 → v2)** — existing token renamed, removed, or
  semantically redefined; CORS posture changed; Cache-Control
  changed in a way that affects propagation; the `Version: vN` body
  comment changes. **Breaking changes require coordinated consumer
  updates at `play.legendary-arena.com` and
  `cards.legendary-arena.com` BEFORE the new tokens publish, per
  `01-VISION.md` Cross-site contract.** That coordination is its own
  WP, not this one.

If the WP is breaking and no coordinated-consumer WP is queued in
`03-ROADMAP.md`, pre-flight is **NOT READY**.

For brand-tokens edits, also confirm:

- [ ] The `Version: vN` body comment is updated correctly
- [ ] `docs/brand/CHANGELOG.md` will gain an entry on lock
- [ ] The bundled fallback in any consumer (e.g.,
      `apps/arena-client/public/brand-tokens.local.css` per the
      WP-007a hash-parity contract) will be refreshed in lockstep

### Known Failure Modes Lens

Scan the WP plan against the failure modes below. For each, assign one
of:

- `PASS` — the WP plan **explicitly prevents** the failure
- `RISK` — prevention is implicit, weak, or missing; attach a
  scope-neutral fix
- `BLOCK` — the WP would trip the failure if executed as drafted; fix
  before authorizing

**General failure modes** (adapted from the engine repo's
`docs/ai/REFERENCE/01.7-copilot-check.md` — re-stated here in
marketing-repo terms):

1. **Cross-site contract drift** — `brand-tokens.css` v1 → v2 change
   ships without coordinated consumer update; or hash-parity between
   live www file and bundled fallback at `play.*` / `cards.*` is
   broken silently. Early signal: the WP names every consumer that
   depends on the contract and confirms each is updated in lockstep
   or is explicitly out of scope.
2. **Scope creep during "small" packets** — the allowlist starts at
   "one file" and grows to a refactor mid-execution. Pair with the
   Site-Affecting Paths list under §Scope Lock above. Early signal:
   the WP names allowed and forbidden globs explicitly; `git diff
   --name-only` is part of the WP's exit criteria.
3. **Missing "why" for invariants** — a Cloudflare zone setting (AI
   Crawl Control OFF, Managed `robots.txt` OFF, Browser Cache TTL
   "Respect Existing Headers"), `_headers` CORS posture, `_redirects`
   apex 301 mechanism, or `Cache-Control` posture is changed without
   a recorded reason. Early signal: the WP cites the originating
   decision (typically WP-006 lock entry in `01-VISION.md`
   Decisions log) and explains why the change preserves or supersedes
   it.
4. **Ambiguous authority chain** — the WP contradicts a
   higher-authority doc and "fixes" it by reinterpreting the doc.
   Early signal: the WP cites the chain
   (`01-VISION.md > 03-ROADMAP.md > 04-CONTENT-CONVENTIONS.md >
   docs/brand/**`) and resolves any conflict by amending the higher-
   authority doc, not the WP.
5. **Silent vs loud failure** — the WP introduces behavior that fails
   silently when a contract is violated (e.g., a missing
   `brand-tokens.css` doesn't trip a build error; a Lighthouse drop
   doesn't fail CI). Early signal: the WP's exit criteria include
   a mechanical check that fails loudly when the contract is
   broken.
6. **Upgrade / deprecation story** — the WP introduces something that
   will need a coordinated update later (a new token, a new
   `_headers` rule, a new build flag) without naming the upgrade
   path. Early signal: the WP states "no consumer migration needed"
   when true, or names the future coordinated-consumer WP when not.

**Marketing-specific failure modes:**

7. **Brand-tokens cross-site contract drift** — the live
   `https://www.legendary-arena.com/brand-tokens.css` body and any
   consumer's bundled fallback hash diverge after this WP lands.
   Early signal: the WP includes a hash-parity verification step
   (per WP-007a Decisions log entry, the contract is
   `SHA-256(live body) == SHA-256(bundled fallback minus SNAPSHOT
   comment block)`).
8. **Cloudflare zone-setting drift** — Browser Cache TTL reverts to
   a CF default and overrides `_headers`; AI Crawl Control toggles
   ON and CF injects a `Content-Signal:` directive into
   `robots.txt`; Managed `robots.txt` toggles ON; a stray Page Rule
   or Redirect Rule is added. Early signal: the WP either confirms
   no zone-state change (`N/A`) or names the exact zone setting,
   the from/to value, and the verification probe.
9. **Lighthouse regression** — Performance, Accessibility, Best
   Practices, or SEO drops below 90 on the home page, blog index,
   or any pillar page after the WP lands. Early signal: the
   §Test / Quality Baseline above is filled in with current scores
   and the WP's exit criteria assert "no category drops below the
   recorded baseline value."
10. **Build reproducibility drift** — two consecutive `npm ci && npm
    run build` produce non-byte-identical `public/`. Early signal:
    the WP includes a reproducibility re-check in its exit criteria
    (`Compare-Object` over SHA-256 hashes, expected empty).
11. **Apex redirect regression** — `https://legendary-arena.com/`
    returns 200 with content instead of 301 to www, or stops
    preserving query string. Early signal: the WP either confirms
    no apex / zone-rule change (`N/A`) or includes a probe step
    (`curl -I https://legendary-arena.com/some/path` returns 301
    with `Location: https://www.legendary-arena.com/some/path`).
12. **Pagefind regression** — index bloat, broken keyboard
    shortcuts (`/`, `Ctrl+K`, `Cmd+K`), empty result set on a
    known-indexed term, lazy-load contract violation (default UI
    bundle loaded eagerly), or the Fuse.js fallback re-introduced.
    Early signal: the WP either confirms no Pagefind change
    (`N/A`) or explicitly preserves the WP-005 contract clauses.
13. **Submodule pointer drift** — `themes/PaperMod` SHA changes
    without an explicit theme-bump WP. Early signal: pre-flight
    records the start SHA in §Test / Quality Baseline; exit
    criteria assert SHA unchanged or include a deliberate bump
    entry.

A clean pre-flight has `PASS` on every item or `RISK` with attached
fixes. Any `BLOCK` flips the verdict to **NOT READY**.

---

### Verdict

Binary outcome:

- [ ] **READY TO EXECUTE** — all sections above are filled in with
      concrete content; all blockers resolved; reviewer signs and
      dates below.
- [ ] **NOT READY** — written reason and path to resolution. Pre-flight
      cannot be re-run until the blocker is cleared.

Reviewer: `<name>`
Date: `<YYYY-MM-DD>`

A `READY TO EXECUTE` verdict authorizes generation of the session
execution prompt at `docs/ai/invocations/session-wpXXX-*.md`. It does
not authorize any code change.

A `NOT READY` verdict is itself the audit artifact — keep it. The
next pre-flight run cites it.

## Lessons Learned Template

Run this after the WP locks. The goal is to capture preventable gaps
that pre-flight should have caught — so the next WP doesn't relearn
them.

**WP:** `WP-XXX`
**Lock date:** `<YYYY-MM-DD>`
**Pre-flight verdict on the day:** READY TO EXECUTE / NOT READY (with
amendment at `<date>`)

For each gap surfaced during execution, fill in:

- **What surprised the executor** — the gap, in one sentence
- **Where pre-flight would have caught it** — which section above
  should have surfaced this; if none would, propose a new bullet or
  section
- **What the spec was insufficiently precise about** — the WP, the
  roadmap row, the vision clause, or the brand doc that needed
  tightening
- **Amendment to land** — the concrete edit to `01-VISION.md`
  Decisions log, this doc's Precedent Log, the WP body, or any other
  governance doc

If no gap surfaced, write:

> No preventable gaps. Pre-flight signals were sufficient.

A WP that locks cleanly with no lessons learned is the goal — not a
red flag.

## Cross-Repo Note

The Legendary Arena engine monorepo
(`C:\pcloud\BB\DEV\legendary-arena`) has its own pre-flight + copilot
check at `docs/ai/REFERENCE/01.4-pre-flight-invocation.md` and
`docs/ai/REFERENCE/01.7-copilot-check.md`, scoped to Execution
Checklists (ECs), boardgame.io `G`-mutation, determinism via
`ctx.random.*`, and the WP class taxonomy (Contract-Only / Runtime
Wiring / Behavior / Infrastructure). That stack does not exist in
this repo.

The two pre-flights are **parallel and independent**. A dual-repo WP
(e.g., the WP-007a precedent that touched both
`apps/arena-client` in the engine repo and lock metadata in this
repo) runs both pre-flights independently — they do not share
artifacts, verdicts, or precedent logs. Each repo's hook chain
validates its own commit log and its own contracts.

A breaking change to the cross-site contract is the one place the
two repos must coordinate. Per `01-VISION.md` Cross-site contract
and `04-CONTENT-CONVENTIONS.md` § CORS contract for
`/brand-tokens.css`, a v1 → v2 brand-tokens bump requires consumer
updates **before** the new tokens publish — that coordination is
its own marketing-repo WP that names every consumer site, with the
engine-repo bundled-fallback refresh in lockstep. Pre-flight in
either repo for a v2 bump must surface the other repo's WP as a
prerequisite or block.

## Hook Discipline During Pre-Flight

Pre-flight does not commit code, but the lessons-learned step often
commits this doc, the WP body, or `01-VISION.md`. Every commit must
pass `.githooks/pre-commit` and `.githooks/commit-msg` per
`01.3-commit-hygiene.md`.

If a hook fails — long line, link checker, forbidden file in staging —
**fix the underlying issue and create a new commit**. Do not use
`--no-verify`. Do not amend a commit that a hook just rejected (the
commit didn't happen; `--amend` would silently rewrite the previous
commit). Pre-flight discipline applies to its own paperwork.
