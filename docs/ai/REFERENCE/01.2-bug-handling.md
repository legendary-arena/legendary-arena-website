# 01.2 — Bug Handling Protocol

> **REFERENCE DOCUMENT — Not an execution prompt. No output required.**
>
> **Subordination (descending authority):**
> 1. `docs/01-VISION.md` (vision, global invariants, decisions log)
> 2. `docs/03-ROADMAP.md` (work packet catalog and execution order)
> 3. `docs/04-CONTENT-CONVENTIONS.md` (content authoring rules)
> 4. `docs/ai/REFERENCE/01.3-commit-hygiene.md` (commit message contract)
>
> If any conflict exists → higher authority wins immediately.

---

## Purpose

Once a Work Packet (WP) is locked, every observed bug is treated as an
**execution contract violation**. This protocol replaces ad-hoc
debugging and enforces:

- Determinism between commits and shipped output
- Specification traceability for every fix
- Zero drift between implementation and the WP / vision contract
- A defensible record of what changed and why

This matters more here than in a typical marketing site because:

- The site is the public face of Legendary Arena
- `static/brand-tokens.css` is a cross-origin API contract consumed
  by `play.legendary-arena.com` and `cards.barefootbetters.com` —
  silent drift breaks downstream consumers
- WP-006 locked the production deploy with mechanical reproducibility
  invariants (same commit → byte-identical `public/`); a regression
  that breaks reproducibility breaks the deploy story

---

## Core Invariant (Non-Negotiable)

Every observed bug MUST be classified into **exactly one** of two
categories:

1. **Implementation violation** — the site implementation fails to
   satisfy a valid clause of a locked WP, of `docs/01-VISION.md`
   (Global invariants / Cross-site contract / Decisions log), or of
   `docs/brand/**`.
2. **Specification error** — the WP, `docs/03-ROADMAP.md`,
   `docs/01-VISION.md`, or `docs/brand/**` contains an inconsistency
   that prevents deterministic interpretation.

This is a **closed classification system**. The following are
**INVALID diagnoses**:

- "Unexpected behavior"
- "Edge case"
- "Worked before"
- "Seems incorrect"
- "Just a small issue"
- "Cosmetic"

If a bug cannot be classified into one of the two categories → **it
is not yet understood**. Do not fix it. Improve the WP / vision
language first (Step 3 below).

---

## Scope

This protocol applies once **any WP is locked** (`✅ Done` in
`docs/03-ROADMAP.md`). Pre-lock bugs surface during WP execution and
are handled by the WP itself; the WP body is the bug protocol while
it's in flight.

Post-lock surfaces governed by this protocol:

- The live production site at `https://www.legendary-arena.com/`
- The apex redirect at `https://legendary-arena.com/`
- The cross-site contract at `https://www.legendary-arena.com/brand-tokens.css`
- Pagefind search infrastructure (locked under WP-005)
- The Cloudflare Pages deploy mechanism (locked under WP-006)
- Any locked content (locked under WP-004 or future content WPs)
- Any locked brand artifact under `docs/brand/**`

## Bug Intake Rule (Mandatory Gate)

When any anomaly is observed (Lighthouse regression, visual drift,
CORS error in DevTools, broken link, Pagefind search failure, brand
parity issue with `play.*` / `cards.*`, deploy failure, build
non-reproducibility, etc.):

1. Open `docs/03-ROADMAP.md` and locate the governing WP (the WP
   whose surface the bug touches).
2. Open the WP file in `docs/ai/work-packets/`.

**Before doing anything else:**

- ❌ Do NOT open `layouts/`, `assets/`, `content/`, `static/`, or
  `hugo.toml`.
- ❌ Do NOT edit CSS or templates to "see if it fixes it."
- ❌ Do NOT run `hugo --minify` to "diff against expected output."
- ❌ Do NOT add browser console logs or DevTools overrides.
- ❌ Do NOT modify the WP to fit observed behavior.

**Invariant:**

> All investigations begin from specification, not implementation.

Violation of this rule = protocol breach. The cost of opening code
first is that you start fitting the spec to the code instead of the
other way around.

---

## Diagnosis Sequence (Strict Order)

Follow these steps exactly. Stop at the first step that classifies
the bug.

### Step 1 — WP Clause Violation Check (Default Path)

Identify the specific clause of the governing WP that the
observed behavior violates. Marketing-repo WPs use these clause
types (analogous to engine-repo EC clauses):

| WP Clause | What it locks |
|---|---|
| **Definition of Done** | Bullet list of what must be true at lock |
| **Exit criteria** | Mechanical thresholds (Lighthouse ≥ 90, etc.) |
| **Failure conditions** | Explicit anti-patterns that fail the WP |
| **Constraints** | What MUST NOT change |
| **Cross-site contract** | The brand-tokens API contract clauses |
| **Rollback** | The pre-WP state and the way back |
| **Goal / Deliverables** | The intended surface |

Evaluate the observed behavior against the **literal text** of
the WP. Don't paraphrase. Don't infer intent. Read what the WP
actually says.

Also check `docs/01-VISION.md`:
- **Global invariants** section (e.g., reproducibility, no
  retroactive breakage, brand tokens as API contract)
- **Cross-site contract** section (the v1 → v2 coordinated-consumer
  rule)
- **Decisions log** entries that constrain the surface

If a clause is violated → **Classification: Implementation
violation**. Proceed to "Implementation Fix" below.

### Step 2 — Specification Consistency Check

Only if Step 1 yields no violation. Read in this exact order:

1. The governing WP
2. `docs/03-ROADMAP.md` (the WP's row in the table, dependency
   chain, parallelization notes)
3. `docs/01-VISION.md` (vision, global invariants, decisions log)
4. `docs/brand/**` (if a brand surface is involved)
5. `docs/04-CONTENT-CONVENTIONS.md` (if content authoring is
   involved)

Ask:

- Does the WP contradict `01-VISION.md` Global invariants?
- Does the WP contradict its row in `03-ROADMAP.md`?
- Does the WP contradict a Decisions log entry?
- Are locked values different between WP and brand docs (e.g.,
  brand-token version, Lighthouse threshold, Cache-Control
  posture)?
- Is the WP language ambiguous enough that two readers could
  interpret it differently? (Ambiguity is a defect, not a
  feature.)

If an inconsistency is confirmed → **Classification:
Specification error**. Stop coding immediately and follow
"Specification Fix" below.

### Step 3 — Specification Insufficiency (Escalation)

If neither violation nor inconsistency can be proven after Steps
1 and 2, the bug is **not the system's fault — it's the spec's**.
The specification is insufficiently precise to classify the
behavior.

Rules:

- Do NOT fix code. The code can't be wrong against a spec that
  doesn't constrain it.
- Do NOT guess what "should" happen.
- Improve the WP, ROADMAP, or VISION language **FIRST**.
- Only after the spec is tightened: restart from Step 1.

This is a real failure mode: when the spec is insufficient, fixing
code reproduces the same insufficient-spec bug on the next
regression. The cure is to make the spec precise enough that the
bug is mechanically classifiable.

## Permitted Fix Types

### Implementation Fix (Default Path)

**Condition:** A valid WP / vision / brand clause is violated by
the current site implementation.

Rules:

- Modify site files only (`layouts/`, `assets/`, `static/`,
  `content/`, `hugo.toml`, `themes/` submodule pointer if
  warranted).
- NEVER weaken or reinterpret the violated clause to fit the
  current implementation.
- NEVER edit the WP file during an implementation fix (drift
  prevention).
- The fix MUST trace to a specific clause (Traceability
  Requirement, below).
- Re-run the WP's Exit criteria and Definition of Done checks
  after the fix lands.
- Commit message: `WP-NNN: <fix description>` per
  `docs/ai/REFERENCE/01.3-commit-hygiene.md`.

### Specification Fix (Controlled Path)

**Condition:** The WP cannot be satisfied without breaking
`01-VISION.md` Global invariants, the Cross-site contract, or
another locked WP's surface.

Rules:

- STOP all site edits immediately.
- Update the relevant doc first:
  - WP body (post-lock amendments allowed; explain in commit body)
  - `docs/03-ROADMAP.md` (WP table or dependency chain)
  - `docs/01-VISION.md` (Decisions log entry recording the change)
  - `docs/brand/**` (only if the change is a v1 → v2 brand contract
    bump, which requires coordinated consumer updates per
    `01-VISION.md` Cross-site contract)
- Record a Decisions log entry in `docs/01-VISION.md` with the
  date, the change, and the rationale.
- Re-run the WP's Exit criteria against the updated spec.
- Commit message: `SPEC: <description>` per
  `docs/ai/REFERENCE/01.3-commit-hygiene.md` (since the change is
  governance, not site).

A specification fix that touches `static/brand-tokens.css` is a
**special case** — it is a cross-site contract change. Per
`01-VISION.md` Cross-site contract, breaking changes (v1 → v2)
require coordinated consumer updates BEFORE the new tokens publish.
That coordination is its own WP, not a SPEC: commit.

---

## Traceability Requirement (Mandatory)

Every fix MUST be mechanically traceable to one of:

- A specific WP clause (Implementation fix), cited in the commit
  body — e.g., "Fixes WP-006 Exit criterion 'Apex returns 301';
  observed 200 with duplicate content on
  `https://legendary-arena.com/`."
- A `docs/01-VISION.md` Decisions log entry (Specification fix),
  cited by date — e.g., "Per 2026-05-09 Decisions log entry on
  apex-redirect mechanism amendment."

If traceability cannot be established:

→ The fix is **invalid**. Stop and re-classify per Step 1 / Step 2.

This requirement is the audit hook: `git log --grep` over WP / SPEC
prefixes, combined with the cited clause / decision, gives any
future reader a complete trace from observed bug → governance
clause → resolution. Without traceability the log degrades into
folklore.

---

## Prohibited Responses (Zero Tolerance)

- Adding inline `style` overrides or `<script>` tags to "patch"
  observed behavior.
- Editing CSS in DevTools and copy-pasting into the repo without
  classifying the bug first.
- Modifying `hugo.toml` or PaperMod overrides to mask a clause
  violation.
- Weakening Lighthouse thresholds in a WP because the current
  score doesn't pass (this is editing the spec to fit the code).
- Bypassing `docs/03-ROADMAP.md` lookup ("I know which WP this is").
- Touching `static/brand-tokens.css` without an explicit WP scope
  for the change.
- Skipping the snapshot-hash check after touching brand tokens
  (the hash-parity invariant exists to catch silent drift).
- Using `--no-verify` to bypass commit hooks (see
  `01.3-commit-hygiene.md` § Bypassing Hooks).
- Speculating about Cloudflare zone settings without checking the
  actual current zone state (zone settings drift silently — verify,
  don't assume).

## Marketing-Site Bug Taxonomy

The two-category model classifies any bug, but recognizing common
shapes speeds Step 1. The following are the bug types this site
actually faces (not exhaustive):

### Visual / brand drift

- Visual regression vs www brand identity (color, type, spacing)
- Header / footer rendering issue
- Brand-token consumption failure (e.g., `var(--la-color-*)` not
  applying — usually a fallback ordering bug)
- Mobile responsiveness break
- Class-color subsystem misuse (per `docs/brand/palette.md §4.4`)

**First-check clauses:** WP DoD, `docs/brand/palette.md`, `docs/brand/strategy.md §5` (layout patterns), `docs/brand/strategy.md §10` (failure modes).

### Performance / quality regression

- Lighthouse score drops below ≥ 90 in any category
- LCP / CLS / TBT degradation
- Bundle bloat (Pagefind index, theme CSS, JS)

**First-check clauses:** WP Exit criteria (Lighthouse scores), `01-VISION.md` Success criteria, WP-005 Pagefind lazy-load contract.

### Functional regression

- Pagefind search broken or returning empty
- Internal link 404s
- CTA button non-functional or missing
- Search keyboard shortcuts (`/`, `Ctrl+K`, `Cmd+K`) broken
- Apex redirect not 301'ing to www

**First-check clauses:** WP-004 (CTA contract), WP-005 (Pagefind UI + keyboard policy), WP-006 (apex redirect zone Redirect Rule), WP DoD checkboxes.

### Build / deploy regression

- `npm ci && npm run build` fails locally
- Cloudflare Pages build fails
- Reproducibility hash drift (two consecutive builds produce
  different `public/`)
- Submodule pointer drift on `themes/PaperMod`

**First-check clauses:** WP-005 reproducibility check, WP-006 pinned env vars (`HUGO_VERSION=0.161.1`, `NODE_VERSION=22`), `01-VISION.md` Global invariants (same commit → same output).

### Cross-site contract regression

- `brand-tokens.css` CORS regression
  (`Access-Control-Allow-Origin: *` missing or different)
- `Cache-Control` drift (zone-level "Browser Cache TTL"
  overriding `static/_headers`)
- `Version: v1` body header missing or wrong
- Hash mismatch between live www file and bundled fallback at
  `play.*` or `cards.*`

**First-check clauses:** WP-006 CORS posture, `01-VISION.md` Cross-site contract, WP-007a / WP-007b cross-site contract sections.

### SEO / accessibility regression

- `sitemap.xml` or `robots.txt` regression
- AI Crawl Control / Managed `robots.txt` toggle drift (CF zone
  setting must remain OFF per WP-006 lock)
- Heading hierarchy broken
- Alt-text missing

**First-check clauses:** WP-006 lock entry on AI Crawl Control + Managed robots.txt, WP-008 (when locked) SEO contract.

## Regression Rule

When a previously resolved bug reappears in production:

→ This is **proof of insufficient specification precision** in the
governing WP.

Required action (in order):

1. Identify the WP clause that should have prevented the
   regression. If no clause covered it, the WP needs a new
   Constraint, Failure condition, or Exit criterion.
2. Strengthen the WP language:
   - Add a Failure condition that names the regression shape.
   - Tighten an Exit criterion to mechanically detect it.
   - Add a Constraint that prevents the underlying cause.
3. Record the WP amendment in `docs/01-VISION.md` Decisions log
   with the date and the regression that drove the tightening.
4. Then apply the normal Implementation Fix procedure against the
   strengthened spec.

**Invariant:**

> Regressions improve specifications, not just code.

A regression that produces only a code fix is a missed
opportunity — the next operator will hit the same bug because the
spec didn't change.

---

## Completion Rule

A bug is resolved ONLY when **all** of the following are true:

- [ ] Every clause of the governing WP is satisfied (re-run DoD
      and Exit criteria checks).
- [ ] No other locked WP is incidentally violated (regression
      check against adjacent surfaces).
- [ ] Cross-site contract still holds (hash-parity check on
      `brand-tokens.css` if brand work was touched; CORS check if
      headers were touched).
- [ ] Reproducibility still holds (two consecutive
      `npm ci && npm run build` produce byte-identical `public/`
      per WP-005 § Step 8.7).
- [ ] Fix is traceable in git to a WP clause or a `01-VISION.md`
      Decisions log entry.
- [ ] If a regression: WP language is strengthened per the
      Regression Rule.

**Passing a single visual check alone is insufficient.** The
mechanical re-verification is what closes the bug.

---

## Enforcement Summary

| Rule | Effect |
|---|---|
| No WP lookup → no edits | Guarantees spec-first debugging |
| Two-category classification | Eliminates ambiguous diagnoses |
| Strict diagnosis sequence | Prevents premature fixes |
| Traceability required | Enables `git log` audit + determinism |
| Regression strengthens WP | Hardens specification over time |
| Completion = mechanical recheck | Closes bugs against the contract |
