## Purpose

Every commit to the marketing-site repository must be mechanically
traceable — via its commit subject line and enforced hooks — to exactly
one of:

- a **Work Packet** (`WP-NNN`),
- a **content-lane edit** (`FIX:` — typo, copy tweak, broken link),
- a **new blog post** (`POST:` — content lane),
- a **roadmap-only change** (outside any single WP),
- an **infrastructure change** (tooling, hooks, CI, scripts), or
- a **specification correction** (governance docs outside any WP).

This document defines the commit message contract, the enforcement
hooks, and the installation and recovery procedures that ensure this
traceability.

Why it matters: this site is the public face of Legendary Arena. The
git log is read by future contributors, by the cross-site brand-token
contract's downstream consumers (`play.legendary-arena.com`,
`cards.legendary-arena.com`), and by anyone auditing what changed
between a deploy and a regression. A disciplined log is a load-bearing
artifact, not a nice-to-have.

---

## Installation

Run once after cloning (or after hooks are updated):

```pwsh
pwsh scripts/git/install-hooks.ps1
```

This sets `git config core.hooksPath .githooks` for the local repo.
Hooks are then active for every subsequent commit until you reinstall
elsewhere or delete the `.githooks/` directory.

The install is **repo-local** — it does not touch your global git
config and does not affect other repositories on your machine.

## Commit Message Format (Enforced by Hooks)

Every commit subject line must match one of these four prefixes.

### Work-packet-scoped commits

```
WP-NNN[a-z]?: <present-tense summary>
```

**Required** when staged files include anything site-affecting (see
"Site-affecting paths" below — i.e., anything that ends up in
`public/` after `hugo --minify`).

Letter suffix accepts parallel-track WPs (e.g., `WP-007a`, `WP-007b`).

Examples:
- `WP-006: lock — Cloudflare Pages deploy verified, scores recorded`
- `WP-007a: wire brand-tokens cross-origin link in arena-client`
- `WP-007b: refine — strict integration mode, phase boundaries`
- `WP-002: bump brand-tokens to v1 final`

### Content-lane edits (typos, copy tweaks, broken links)

```
FIX: <present-tense summary>
```

**When to use:** small content corrections that don't change site
structure, navigation, configuration, layouts, or the brand-tokens
contract. Typo on the About page. Reworded paragraph in a blog post. A
broken outbound link in a marketing page. A missing alt text.

**Path allowlist (hook-enforced).** A `FIX:` commit may only stage:

- `content/**` — any page or post markdown body
- `static/images/**` — image assets that travel with content (per
  `04-CONTENT-CONVENTIONS.md` §Images)

Any staged file outside this allowlist that is also site-affecting
(layouts, archetypes, brand-tokens, `_headers`, `_redirects`,
`hugo.toml`, `package.json`, themes, data, i18n, non-image `static/`)
forces the commit back to `WP-NNN:` with a proper WP file.

**Ceremony skipped, ceremony kept.** A `FIX:` commit:

- does NOT require a WP file in `docs/ai/work-packets/`
- does NOT require a pre-flight invocation (`01.4`)
- does NOT require session notes
- DOES still run pre-commit and commit-msg hooks (forbidden words,
  ≥12-char subject, secrets/build-output scrubbing)
- DOES still go through a PR (same `claude/*` → squash-merge flow as
  WP work — keeps the second pair of eyes on the diff before live)

Examples:
- `FIX: correct "recieve" -> "receive" on /about/`
- `FIX: replace dead link in launch announcement post`
- `FIX: tighten hero subheadline copy on /`

### New blog post

```
POST: <YYYY-MM-DD — present-tense summary>
```

Same path allowlist and same ceremony rules as `FIX:`. The date in the
subject mirrors the post's filename date prefix
(`content/posts/YYYY-MM-DD-<slug>.md` per
`04-CONTENT-CONVENTIONS.md` §Slugs) so the commit log self-documents
the publishing date independent of the author timestamp.

**Permitted staged files for POST:**

- `content/posts/YYYY-MM-DD-<slug>.md` — the post body
- `static/images/posts/<slug>/**` — the post's image assets (optional)

If you find yourself touching `_index.md` (section navigation),
front-matter taxonomy data, or a new section, that's a WP, not a POST.

Examples:
- `POST: 2026-05-12 — launch announcement v2 with deck embed`
- `POST: 2026-06-12 — five-finger shoes for trail running`

Helper:
- `pwsh scripts/git/new-post.ps1 -Slug "<kebab-case-slug>"` runs
  `hugo new posts/...` against `archetypes/posts.md` so front-matter
  stays consistent with `04-CONTENT-CONVENTIONS.md` §Front-matter.

### Roadmap-only changes (outside any WP)

```
ROADMAP: <summary>
```

Use when editing `docs/03-ROADMAP.md` for reasons that don't fit a
single WP — pointer lines, table restructuring, cross-reference fixes,
appendix additions, status-legend updates.

Examples:
- `ROADMAP: pointer line — wiki search at ewiki is engine-repo work`
- `ROADMAP: restructure WP table — split locked from pending`

Forbidden: combining a `ROADMAP:` commit with site-affecting file
edits. If a roadmap change is part of a WP lock, use `WP-NNN:` for the
whole lock commit (which typically updates roadmap + vision + WP body
together).

### Infrastructure (tooling, hooks, CI)

```
INFRA: <summary>
```

Examples:
- `INFRA: add commit-msg + pre-commit hooks`
- `INFRA: gitignore — add lighthouse-*.json local verification artifacts`
- `INFRA: pin Hugo version in .nvmrc`
- `INFRA: bump pagefind to 1.5.3 — security patch`

Use for: `.githooks/**`, `scripts/**`, `.github/**`, `.gitignore`,
`.gitattributes`, `package.json` dev-dep bumps, `README.md`,
`LICENSE`, top-level config files that aren't `hugo.toml`.

Forbidden: combining `INFRA:` with site-affecting file edits.

### Specification corrections (rare)

```
SPEC: <summary>
```

Use when fixing inconsistencies in `docs/01-VISION.md`,
`docs/03-ROADMAP.md`, `docs/04-CONTENT-CONVENTIONS.md`,
`docs/brand/**`, or other governance docs **outside a WP context**.
Not for site changes; not for WP body edits.

Examples:
- `SPEC: clarify brand-tokens cross-site contract — v2 bump rule`
- `SPEC: fix dead link in vision.md decisions log`

If you're tempted to use `SPEC:` for a non-trivial change that
deserves its own WP, write the WP instead. `SPEC:` is for surgical
corrections, not redesigns.

## Site-Affecting Paths

The hook enforces `WP-NNN:` prefix when any of these are staged:

| Path pattern | Why it's site-affecting |
|---|---|
| `content/**` | Source markdown for pages and posts |
| `layouts/**` | Hugo templates / overrides (incl. PaperMod) |
| `assets/**` | Pipeline-processed CSS / JS |
| `static/**` | Pass-through assets (incl. `brand-tokens.css`, `_headers`, `_redirects`) |
| `archetypes/**` | Hugo content archetypes |
| `data/**` | Hugo data files consumed by templates |
| `i18n/**` | i18n strings consumed by templates |
| `themes/**` | PaperMod submodule pointer |
| `hugo.toml` | Site config |
| `package.json`, `package-lock.json` | Pagefind / build dependency lockfile |

Any file matching the above triggers the **WP-NNN: requirement** —
**unless** every site-affecting file in the commit is within the
**content lane** (`content/**` + `static/images/**`), in which case
`FIX:` or `POST:` is also accepted. See §Content-lane edits above for
the rule.

Documentation under `docs/**` is **not** site-affecting by this rule —
docs are governance, not shipped output — so `docs/03-ROADMAP.md`
edits can carry any prefix (typically `WP-NNN:` if part of a WP lock,
`ROADMAP:` otherwise).

## Brand-Token Contract Discipline (Convention)

`static/brand-tokens.css` is the cross-site API contract consumed by
`play.legendary-arena.com` and `cards.legendary-arena.com`. Edits to
this file are load-bearing for downstream consumers.

Convention (not hook-enforced, but reviewer-enforced):

- Any change to `static/brand-tokens.css` MUST be part of a WP whose
  scope explicitly covers the brand-tokens contract (e.g., WP-002,
  WP-003, or a future v1 → v2 bump WP).
- The commit message body should reference the version header in the
  file (`Version: vN`) and call out whether the change is additive
  (forward-compatible) or breaking (requires coordinated consumer
  update).
- `docs/01-VISION.md` decisions log should carry an entry for any
  brand-tokens change.

If hook enforcement of this convention is later adopted, it must be
added behind a feature flag and announced in the vision decisions log
first.

## Forbidden Patterns (Rejected by Hooks)

The following words in commit subjects cause automatic rejection:

`WIP`, `wip`, `fix stuff`, `misc`, `tmp`, `updates`, `changes`,
`debug`, `quick fix`, `hotfix`, `cleanup`, `refactor`

Subject must be at least **12 characters** after the prefix.

Why these are forbidden: they are placeholders that defer the work of
describing what changed. In a public-facing repo that downstream
consumers depend on, "fix stuff" obscures whether a brand-tokens
change broke `play.*` or just renamed a partial. Write the concrete
description.

If you genuinely need to commit something temporarily during a
multi-step rebase or merge resolution, use the helper script's
`-Check` mode to validate the message before committing, and frame
the change as `INFRA:` if it's tooling or `WP-NNN:` if it's part of
in-flight WP work.

## Hook Architecture

| Hook | Fires when | Enforces |
|---|---|---|
| `pre-commit` | Before message is written | No `.env`, no `node_modules/`, no `public/`, no `resources/`, no `.hugo_build.lock`, no credentials, no `lighthouse-*.json` |
| `commit-msg` | After message is written | Prefix format, forbidden words, ≥12-char subject body, WP file existence, site-affecting-files-require-WP-prefix |

### What `commit-msg` validates for `WP-NNN:` commits:

1. WP file exists: `docs/ai/work-packets/WP-NNN[a-z]?-*.md`
   (lookup is case-insensitive so `WP-007A:` resolves
   `WP-007a-*.md` and vice versa)
2. If site-affecting files are staged, prefix must be `WP-NNN:`
   (not `ROADMAP:`, `INFRA:`, or `SPEC:`)

### What `commit-msg` validates for `ROADMAP:` / `INFRA:` / `SPEC:` commits:

- No site-affecting files staged. If a site-affecting file is
  staged with a non-WP prefix, the commit is blocked with a hint
  to use `WP-NNN:` instead.

## Using the Helper Script

```pwsh
# Interactive mode — prompts for message
pwsh scripts/git/wp-commit.ps1

# Direct mode
pwsh scripts/git/wp-commit.ps1 -Message "WP-007b: refine — phase boundaries"

# Stage all modified files + commit
pwsh scripts/git/wp-commit.ps1 -All -Message "INFRA: add commit hygiene hooks"

# Stage specific files + commit
pwsh scripts/git/wp-commit.ps1 -Files "content/_index.md","layouts/index.html" -Message "WP-004: home hero copy edit"

# Dry-run (validate without committing)
pwsh scripts/git/wp-commit.ps1 -Check -Message "WP-007b: <summary>"
```

The helper verifies hooks are installed before committing and offers
to install them if they're not.

## Bypassing Hooks

`git commit --no-verify` bypasses all hooks. This is **prohibited
under normal operation** unless explicitly approved by a human.
Claude (or any AI assistant) must never use `--no-verify` or
`--no-gpg-sign` unless the user requests it.

### Emergency Override (Last Resort)

In case of repository corruption or hook malfunction, hooks may be
bypassed ONLY by temporarily renaming `.githooks/`:

```pwsh
Rename-Item .githooks .githooks-disabled
# ... perform recovery commit ...
Rename-Item .githooks-disabled .githooks
```

This must be immediately reverted after recovery. Commits made this
way must be annotated in their body (`Override: hooks disabled —
<reason>`) and reviewed at the next PR.

## Common Errors and Fixes

| Error | Cause | Fix |
|---|---|---|
| "Subject does not match an allowed prefix" | Missing `WP-NNN:`, `ROADMAP:`, `INFRA:`, or `SPEC:` | Add the correct prefix |
| "Subject too short after prefix" | Description < 12 chars | Write a more specific summary |
| "Subject contains a forbidden pattern" | WIP, misc, tmp, etc. | Use a concrete description |
| "No WP file found for WP-NNN" | WP file doesn't exist | Create the WP first (under `docs/ai/work-packets/`), or use `INFRA:` / `ROADMAP:` / `SPEC:` if not WP work |
| "Site-affecting files staged but commit is not WP/FIX/POST-scoped" | `content/`, `layouts/`, `static/`, etc. staged with `ROADMAP:`/`INFRA:`/`SPEC:` prefix | Use `WP-NNN:` (any site path), `FIX:`/`POST:` (content lane only), or unstage the site files |
| "FIX:/POST: is limited to the content lane" | `FIX:` or `POST:` commit staged out-of-lane files (e.g., `layouts/`, `archetypes/`, `static/brand-tokens.css`) | Use `WP-NNN:` with a WP file, or unstage the out-of-lane files |
| "Staged `.env` file detected" | `.env` in staging | `git reset HEAD .env` |
| "Staged `public/` files detected" | Build output staged | `git reset HEAD public/` — `public/` is gitignored; if it's staged, something pulled it in |
| "Staged `lighthouse-*.json` detected" | Local verification artifact staged | `git reset HEAD lighthouse-*.json` — these are local-only per WP-005 § Step 8.5 |

## CI Mirror

`.github/workflows/commit-hygiene.yml` runs on every PR to `main` and
re-validates all commits in the PR. This catches commits that bypassed
local hooks (missing install, `--no-verify`, or external contributors
on a fork).

The CI mirror is authoritative and must be treated as a second line of
defense, not a substitute for local hooks. A passing local commit that
fails CI is a hook-drift indicator — investigate before merging.

Three jobs run in parallel:
- **commit-messages** — runs `.githooks/commit-msg` against every PR
  commit
- **file-hygiene** — checks PR diff for forbidden file patterns
  (`.env`, `node_modules/`, `public/`, credentials, `lighthouse-*.json`)
- **wp-site-traceability** — verifies site-affecting commits have
  `WP-NNN:` prefix with an existing WP file, OR carry `FIX:`/`POST:`
  with every site-affecting path inside the content lane

## Cross-Repo Note

The Legendary Arena codebase spans two repositories with **different
commit conventions**:

| Repo | Prefixes | Governance doc |
|---|---|---|
| `legendary-arena-website` (this repo) | `WP-NNN:`, `ROADMAP:`, `INFRA:`, `SPEC:` | this file |
| `legendary-arena` (engine monorepo) | `EC-###:`, `SPEC:`, `INFRA:` | `docs/ai/REFERENCE/01.3-commit-hygiene-under-ec-mode.md` (engine repo) |

The engine monorepo executes against Execution Checklists (EC); this
marketing site executes against Work Packets (WP) directly. If you
work on a WP that spans both repos (e.g., WP-007a which touches
marketing-site lock metadata + engine-repo `apps/arena-client`):

- Commits in this repo use `WP-NNN:` prefix.
- Commits in the engine repo use `EC-###:` prefix, referencing the
  EC that operationalizes the WP on that side.
- The two commits should land near each other in time but do **not**
  need identical commit messages — each repo's hook validates its
  own log.
