## Purpose

A **pre-drafting hygiene check** is a fast, manual gate that runs
**before** opening a new WP drafting session in Claude Code. It exists
to prevent the parallel-coordination trap: drafting a new WP while
another WP is in mid-execution (or another SPEC PR is open against the
same WP file) creates avoidable git pain — rebase + revalidate cycles,
governance-ledger conflicts on `03-ROADMAP.md`, force-pushes to resolve
overlap.

**Empirical precedent (2026-05-11):** WP-007b's execution session and a
parallel hardening pass (SPEC PR #4) both touched the same WP file. The
collision produced 7 inline amendments and significant operator pain
before WP-007b shipped. The lesson: **same-repo parallel work almost
always costs more than it saves.** This doc is the gate that surfaces
the trap before drafting begins, so the operator can run sequential by
default and reserve parallel for cross-repo work.

---

## When to invoke

Run this check before ANY of the following:

- Creating a new WP file in `docs/ai/work-packets/`
- Adding or modifying a `WP-NNN` row in `docs/03-ROADMAP.md`
- Opening a Claude Code session titled "draft WP-NNN" or similar
- Running an audit/hardening pass on an existing WP body

If none of the above is imminent, this doc doesn't apply — proceed
with the regular `01.4-pre-flight-invocation.md` for per-WP readiness.

---

## Hard rule — No parallel draft starts

Starting a new WP draft while another WP draft session is open in
this repo is **prohibited**. This includes:

- Separate terminals
- Separate Claude Code sessions
- Separate worktrees on different `claude/*` branches

**One drafting session at a time, per repo.** This rule directly
encodes the WP-007b lesson: parallel drafts collide on `03-ROADMAP.md`,
on adjacent WP-NNN slots, and on `01-VISION.md` decisions-log entries.
The collision cost is always greater than the parallel-execution
savings.

Cross-repo parallel is unaffected — drafting one WP in this marketing
repo while another WP drafts in the engine repo at
`C:\pcloud\BB\DEV\legendary-arena\` is fine (independent ledgers, no
shared files).

---

## Gate decision (explicit)

- **If ALL checks pass → GO:** drafting may begin
- **If ANY check fails → STOP:** resolve per the listed remediation
  path before drafting

No partial passes. No deferrals. This gate is binary.

---

## Automated form (recommended)

All 6 checks below are implemented as a single PowerShell script:

```pwsh
pwsh scripts/pre-drafting-hygiene-gate.ps1
```

Output:
- `STATUS: GO` (exit 0) — all checks passed; baseline SHA printed
- `STATUS: STOP — <reason>` (exit 1) — failed check + actionable diagnosis

The script is **read-only** (never runs `git pull`, never modifies
branches). It executes the same 6 checks documented below in the same
order, with the same STOP-at-first-fail semantics. The script does
NOT execute the close-ritual (manual operator action), but it surfaces
the cases that require it.

Manual invocation of the checks (below) remains valid — useful when
operators want to inspect intermediate state, run checks against a
non-default repo path, or debug the gate itself.

## Checks (run in order; STOP at the first FAIL)

### Check 0: Repository identity (must be marketing repo)

The script and the manual checks both assume they're running against
`C:\www\legendary-arena-com`. Verify the assumption before any other
gate fires — running the rest of the checks against a wrong repo
produces confidently wrong verdicts.

```pwsh
# 0a: cwd matches expected path
(Get-Location).Path  # Expected: C:\www\legendary-arena-com

# 0b: actually inside a git working tree (not just a path that happens to exist)
git rev-parse --is-inside-work-tree
# Expected: true (exit 0)

# 0c: origin remote points at the marketing repo
git remote get-url origin
# Expected: matches "legendary-arena/legendary-arena-website"

# 0d: structural sanity — key marketing-repo file present
Test-Path docs/03-ROADMAP.md
# Expected: True
```

**If any 0a–0d fails:** STOP. Likely causes:
- Wrong terminal cwd (cd to `C:\www\legendary-arena-com` first)
- Stale checkout (the working tree is missing core files; re-clone or
  `git fetch origin && git reset --hard origin/main` if no local
  work to preserve)
- Wrong fork (origin URL doesn't match; the marketing repo lives at
  `github.com/legendary-arena/legendary-arena-website`)

This check is cheap (~100 ms) and catches the highest-impact category
of operator error (running the gate against the wrong repo entirely).
Never skip it.

### Check 1: Working tree clean

```pwsh
cd C:\www\legendary-arena-com
git status --short
```

**Expected:** no output.

**If output present:** commit, stash, or discard before drafting.
Uncommitted state from a prior session leaking into a new WP draft
creates audit confusion when the new WP's PR diff includes residue
from work that wasn't its own.

**Additional invariants** (FAIL if any of the following — `git status`
can look clean while git state is mid-operation):

- No rebase in progress (`git status` must not show "rebase in
  progress" or list `<<<<<<<`-style conflict markers anywhere)
- No merge conflicts (no conflict markers in the working tree)
- HEAD must be on a named branch, NOT detached (`git symbolic-ref
  --short HEAD` must succeed and return a branch name; if it errors
  with "ref HEAD is not a symbolic ref", you're on a detached HEAD —
  reattach to a branch before drafting)

### Check 2: Canonical synced with origin

```pwsh
git pull --ff-only origin main
```

**Expected:** `Already up to date.` or fast-forward succeeds with
no conflicts.

**If `git pull --ff-only` fails (non-FF state):**

- **DO NOT** retry with `--rebase` or `--merge`
- **DO NOT** draft against a diverged local state

**Resolution paths** (pick exactly one; the underlying state determines
which applies):

1. **Push local commits** if they're intentional (open a PR for them
   first; do not merge directly to main)
2. **Reset hard to origin/main** if local commits are abandoned-state
   from earlier sessions: `git reset --hard origin/main` (destructive
   — verify there's no work to preserve first)
3. **Complete any in-progress rebase/merge first** if one is active
   (`git rebase --continue` / `git rebase --abort` / `git merge
   --continue` / `git merge --abort` as appropriate)

Drafting must begin from a **known-good, synced `origin/main` baseline
only**. The canonical baseline is load-bearing for every gate that
follows.

### Check 3: Prune-script audit reports silent

```pwsh
node scripts/prune-empty-claude-branch.mjs --report
git branch --list 'claude/*' -v
```

**Interpretation rule (tiered):**

- **≤ 4 prunable branches** → informational; drafting MAY proceed
  (`--report` will be silent under the script's threshold of 5)
- **≥ 5 prunable branches** → **FAIL**; cleanup required before
  drafting

```pwsh
# Cleanup path for the ≥5 case:
node scripts/prune-empty-claude-branch.mjs --execute
```

**Exception that overrides the tiered rule:** any `claude/*` branch
with commits ahead of `origin/main` AND no merged PR → **FAIL
regardless of count.** That branch has unmerged work; close it out
via the ritual in `## Closing a claude/* branch` below before
drafting. One unmerged-work branch is enough to trip the parallel-
coordination trap; the count threshold is for noise, not risk.

### Check 4: No open PRs against files the new WP will touch

```pwsh
gh pr list --state open --json number,title,headRefName
```

**Expected:** no open PRs OR open PRs don't touch the files the new
WP plans to edit.

**Files to check overlap against:**
- `docs/03-ROADMAP.md` (every new WP touches this)
- `docs/ai/work-packets/` (especially adjacent WP-NNN slots)
- `docs/01-VISION.md` (if the WP locks a decisions-log entry)
- Any production file the new WP names in its scope

**Mechanical overlap check (recommended over manual reasoning):**

For each open PR branch surfaced by the `gh pr list` above:

```pwsh
git fetch origin <branch>
git diff origin/main...origin/<branch> --name-only
```

Compare the output (files the open PR touches) against the planned
WP-NNN touch set. If the intersection is non-empty (`∩ ≠ ∅`) → FAIL.

This converts "think about overlap" into a deterministic file-list
diff — robust under speed and avoids false-clear from operator
fatigue.

**If overlap exists:** STOP. The parallel-coordination trap is real.
Resolution paths (in order of preference):

1. **Merge the open PR first**, then proceed with the new draft from
   the updated main. This is the structurally simplest path.
2. **Wait** for the PR to resolve via your normal review cadence.
3. **(Last resort)** continue the open PR's work as your "new" WP —
   if the scope genuinely overlaps, two PRs may be one PR in disguise.

### Check 5: No execution session in flight for an active WP

```pwsh
git worktree list
```

**Expected:** just canonical (`C:/www/legendary-arena-com`) plus at
most one auto-spawned worktree for your current Claude Code session.

**Invariant (locked):** at most **ONE active `claude/*` branch per
repo**. The marketing repo's sequential-execution model depends on
this; multiple active sessions in the same repo are the parallel-
coordination trap restated at the worktree layer.

**If multiple worktrees on different `claude/*` branches:** another
session is in flight in this repo. Sequence the work — close out
all but one in-flight session before opening a new drafting one.
See `## Closing a claude/* branch` for the close ritual.

## Closing a claude/* branch (close-ritual)

If Checks 3 or 5 surface a `claude/*` branch that needs to be closed
before drafting can proceed:

**Pre-deletion audit-trace check (mandatory before any branch
deletion):** confirm all relevant reasoning is captured in at least
ONE of:

- The branch's commit messages (commit bodies, not just titles)
- The merged PR description
- The next WP body's `§Context` or `§Assumes` sections

**Branch deletion must not erase reasoning history.** If a decision
the branch encoded isn't durably captured elsewhere, surface it
before pruning — otherwise the audit trail loses the "why."

### Case A: Branch's PR is already merged

From inside the branch's worktree:

```pwsh
node scripts/prune-empty-claude-branch.mjs --verify-current
```

**Expected:** `VERIFY PASS` (via merged-PR fallback if rebase- or
squash-merged; via 0-commits-ahead if true-merge / fast-forward).

Then delete:

```pwsh
git branch -D claude/<name>
git push origin --delete claude/<name>
```

### Case B: Branch has unmerged work that should land

Open or finish the PR for it FIRST. Don't try to draft a new WP while
unmerged work is pending — the file-overlap risk is exactly the
parallel-coordination trap this doc exists to prevent.

### Case C: Branch has unmerged work that should be abandoned

If the work isn't worth landing:

```pwsh
git push origin --delete claude/<name>   # if pushed
git branch -D claude/<name>              # local
```

Document the decision in the next commit's body so future audits can
see why the branch went away.

### Final audit (after close-ritual)

```pwsh
node scripts/prune-empty-claude-branch.mjs --report
```

**Expected:** silent.

## After all checks pass

You're cleared to open a new drafting session. Proceed per
`01.4-pre-flight-invocation.md` to draft the WP file + roadmap row.

### Baseline capture (recommended)

```pwsh
git rev-parse HEAD
```

Record this SHA in your WP draft notes (typically in the WP body's
`§Context` or `§Assumes` block). All drafting from this point
assumes the captured commit as the baseline authority. If pre-flight
or a later gate needs to reproduce the draft's starting state, the
baseline SHA is the canonical reference.

This makes future audit-trail reasoning ("what did `main` look like
when this WP was drafted?") deterministic instead of guesswork.

### Recommended next actions

1. Open Claude Code in this repo (auto-spawn worktree fires; SessionStart hook reports silent per `01.8`)
2. Identify next-free WP number from `03-ROADMAP.md`
3. Read the relevant WP-NNN section in `03-ROADMAP.md` for scope authority
4. Use an existing WP file (e.g., `WP-006-cloudflare-deploy.md` or `WP-007a-play-deploy.md`) as structural template
5. Run `01.4` pre-flight against the drafted WP body
6. Commit per `01.3-commit-hygiene.md` conventions

## Rationale (why this doc exists)

The marketing repo's small governance surface — `03-ROADMAP.md`,
`01-VISION.md`, the WP file collection — means same-repo parallel
work bumps into shared files even when the code surfaces are disjoint.
Two WPs simultaneously add roadmap rows; both reserve adjacent
WP-NNN slots; both touch `01-VISION.md`'s decisions log. Each conflict
costs a rebase + revalidate cycle.

**Sequential within this repo is structurally simpler and faster in
practice.** Cross-repo parallel work (one WP in this marketing repo +
one WP in the engine repo at `C:\pcloud\BB\DEV\legendary-arena\`)
remains genuinely cheap because the repos have fully independent
ledgers.

This hygiene gate is intentionally fast (5 commands, ~2 minutes). The
cost of running it is far less than the cost of discovering a
parallel-coordination conflict mid-drafting and having to rebase out
of it.

---

## No soft bypasses (governance reinforcement)

- A failed check **cannot** be "acknowledged and ignored"
- A warning **cannot** be treated as a pass
- A partial remediation is still a **FAIL**

All checks must fully pass before drafting begins. The cost of
running the checks is bounded (~2 minutes); the cost of drafting on
top of a failed-but-bypassed gate is unbounded (rebase cycles,
audit chaos, force-pushes, mid-execution surprises). The tradeoff
always favors completing the gate.

If a check fails in a way that the documented resolution paths don't
cover, **surface to the operator and STOP**. Treating ambiguity as
permission to proceed is the same failure mode the gate exists to
prevent.
